# Code Review

## 何时使用

在提交 PR、合并主干、或接手他人改动前使用。目标是发现"会导致故障或返工"的问题，而不是统一代码风格。

## 评审顺序

1. **意图**：这个改动要解决什么问题？PR 描述与代码是否一致？
2. **正确性**：边界条件、空值、并发、错误路径是否被覆盖？
3. **安全**：是否引入注入、越权、敏感信息泄露、不安全反序列化？
4. **可维护性**：命名是否表达意图？抽象是否过早或过晚？是否有复制粘贴？
5. **可验证性**：是否有能复现问题的测试？失败场景是否被测到？

## 输出格式

```md
## 结论
- [ ] 可以合并
- [ ] 修改后合并
- [ ] 需要重新设计

## 阻塞项
- 文件:行号 — 问题 — 建议

## 非阻塞建议
- ...

## 已验证
- 我实际运行/检查了什么
```

## 规则

- 每个阻塞项必须给出可执行的修改建议。
- 不要用"建议优化"这类无法验收的措辞。
- 对不确定的点标注"待确认"，并说明需要谁确认。
- 一次评审聚焦最多 5 个关键问题，避免淹没作者。
